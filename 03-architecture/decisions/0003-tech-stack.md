# 0003. Tech stack: SvelteKit frontend, ASP.NET Core API, Docker on a VPS

- **Status:** Proposed
- **Date:** 2026-11-18

## Context

- The next milestone is a **demo website** for a potential partner garden center: course topics and a few encyclopedia entries, read-only, in Hungarian ([concept](../../01-product/concept.md)).
- The knowledge base is stored in **MongoDB** ([ADR-0001](0001-knowledge-base-mongodb.md)). Course topics are **AsciiDoc**, encyclopedia entries are **JSON** ([ADR-0002](0002-content-formats.md)).
- **Sign-in with external providers is part of the demo.** Later the system also needs change notifications, a change stream listener, and eventually interactive garden planning (plot editor, sun map).
- The project uses **separate repositories** per component, for independent pipelines, releases and SonarQube analysis.
- Everything runs on one rented **Contabo VPS** for now. **Traefik is already set up on the VPS** for traffic routing and HTTPS. Monitoring goes to the existing **Grafana Cloud**.
- The developer knows **TypeScript/JavaScript** and **.NET/C#**.
- The content must be indexable by search engines, so pages are rendered on the server.

## Decision

| Part | Choice |
| --- | --- |
| **Frontend** | **SvelteKit** (Svelte, TypeScript), server-side rendering. |
| **AsciiDoc rendering** | **Asciidoctor.js** in the frontend server, with an extension for the project link syntax (`{id, name}` references). |
| **Frontend translations** | UI texts and enum labels in per-language files; **the library is still to be chosen** (open point). |
| **Styling** | **Plain CSS**: Svelte's component-scoped styles and CSS custom properties generated from the design system tokens. No CSS framework. |
| **API** | **ASP.NET Core** (.NET LTS release), Minimal APIs, **MongoDB C# driver**. Read-only REST endpoints for the demo. |
| **API contract** | **OpenAPI** description generated by the API; the frontend's TypeScript client is generated from it. |
| **Database** | **MongoDB**, single-node replica set (needed later for change streams). |
| **Reverse proxy** | **The existing Traefik on the VPS** (already handles HTTPS). New services are attached to it with Docker labels. |
| **Runtime** | **Docker Compose** on the VPS. Images are built by **GitHub Actions** and stored in **GitHub Container Registry**. |
| **Monitoring** | **Grafana Alloy** on the VPS, sending logs and metrics to Grafana Cloud. |
| **Code quality** | **SonarQube Cloud** for every code repository. |
| **Later: listener** | A **.NET Worker Service** subscribing to MongoDB change streams (history, backup, alerts). |
| **Sign-in** | **OpenID Connect with external providers, in the demo already.** The demo supports **Google** only; more providers can be added later. The SvelteKit server handles the sign-in flow; the API validates the tokens. |

### Repositories

| Repository | Content | Needed for the demo |
| --- | --- | --- |
| `sproutpal-web` | SvelteKit frontend | yes |

## Reasons

- **Both languages the developer knows are used where they fit best**: TypeScript in the browser and for server-side rendering; C# for a strongly typed API and, later, a long-running worker.
- **SvelteKit** renders on the server (good for search engines and fast first loads), handles both content pages and the interactive planner that comes later, ships little JavaScript to the browser, and its scoped styles make a CSS framework unnecessary.
- **AsciiDoc in the frontend**: Asciidoctor.js is the maintained JavaScript port of Asciidoctor; the .NET AsciiDoc libraries are less complete. Rendering where the HTML is produced keeps the API a plain data API.
- **A separate API** keeps the database private behind one service, gives a single place to enforce rules (later: write path, `changeNote`, versions), and matches the multi-repository decision.
- **OpenAPI-generated client** keeps the frontend and the API in sync without hand-written types.
- **Docker Compose** is the simplest way to run several services on one VPS, and reusing the existing Traefik avoids a second proxy.

## Alternatives considered

- **Next.js** (React): the largest ecosystem, but heavier; SvelteKit was preferred.
- **Astro**: excellent for content sites, but the interactive planner would need a second approach later.
- **Tailwind CSS**: rejected to avoid another dependency; plain CSS with tokens is enough.
- **A separate reverse proxy (Caddy)**: unnecessary, Traefik already runs on the VPS.
- **One full-stack SvelteKit app reading MongoDB directly**: fastest for the demo, but mixes frontend and backend in one repository and exposes database access to the web tier.
- **Node.js API (NestJS)** instead of ASP.NET Core: one language everywhere, but C# fits the API and worker better and the developer knows it.

## Consequences

- Positive: each part uses a well-supported tool; the demo stack is the production stack, only smaller.
- Positive: the API contract is explicit (OpenAPI), so the frontend and the API can be developed and released independently.
- Negative: two languages and toolchains to maintain (Node.js and .NET).
- Negative: four repositories already for the demo, each with its own pipeline.
- Negative: everything runs on one VPS; if it fails, the whole site is down.
- Negative: sign-in in the demo brings personal data (names, e-mail addresses) into the system from the start, so a privacy notice and account deletion are needed early.

## Open points

- Exact versions (SvelteKit, .NET LTS, MongoDB) are pinned when the repositories are created.
- Which translation library the frontend uses.
- How the frontend calls the API inside the server (internal Docker network) and from the browser (only through Traefik).
- Which further sign-in providers to support after the demo.
